## 1. 왜 바꾸는가 — 현행은 사실상 1단계 전략이다

### 실측 (2026-09-01, VPS 직접 조회)

```
단계2 체결 : 최근 3일  2건
단계3 체결 : 최근 7일  0건          ← 7일간 한 건도 없다

볼밴 분할 08-31 이후 종료 11건
  COMPLETED  5건  평균  +5.79
  STOPPED    6건  평균 -11.59
  승률 45.5% / 손익비 0.50 / 기대값 -3.69 per trade / 필요 승률 66.7%
```

100/200/500 으로 물타서 평단을 낮추고 손절선을 깊게 가져가는 설계인데,
2·3단계가 안 붙어서 **「100 만 넣고 −10% 에 잘리는」** 전략이 되어 있다.

### 막는 곳 (코드 확정)

`stage_trigger_worker.py:865` — Fix 218 블록.
`_is_split and next_stage_no >= 2` 이면 `check_stage_entry_signal` 을 요구한다.

실제 차단 로그 원문:

               정점확인 미충족: 지표 꺾임 0/2 (아직 진행 중 = 정점 아님!)

  RSI  : rsi_prev <= 35.0  AND  rsi_now > rsi_prev

**절대 참이 될 수 없어** 반복저점 조건만 비활성화했다. 남은 차단은 지표 꺾임 2/3 하나다.

## 2. 「최고점」의 정확한 번역 — 이것부터 틀리면 전부 틀린다

볼밴 분할의 단계 트리거가 진입가 대비 **어느 쪽**에 있는지 실측했다:

```
#1937 PROMUSDT SHORT  진입 5.631   단계2 5.747 (+2.06% 위)   단계3 5.859 (+4.06% 위)
#1923 0GUSDT   LONG   진입 0.2091  단계2 0.2050 (-1.95% 아래) 단계3 0.2008 (-3.95% 아래)
```

**SHORT 은 위, LONG 은 아래 — 둘 다 「불리한 방향」이다(물타기).**
간격은 2%p (`stage_gap_pcts`, Fix 209).

### 정의

> **「최고점」 = 진입 방향에 대해 불리한 쪽의 극값.**
> - SHORT → **신고점** (running max)
> - LONG  → **신저점** (running min)

부호 하나로 통일한다 (분기가 2곳 이상이면 반드시 어긋난다 — Fix 251 교훈):

```python
s = +1 if side == "SHORT" else -1     # s·x 가 클수록 「불리」
극값 갱신 = (s * price > s * ext)
```

이 정의가 `stage_trigger_worker.py:814` 및 `pump_split_entry_worker.py:450-453`
(`sign = -1 if LONG else +1`) 와 **이미 같은 방향**이다.

⚠️ LONG 의 극값을 「가격 최고점」으로 잡으면 가격 트리거와 방향이 반대가 되어
수학적으로 진입 불가가 된다. **LONG 은 신저점이다.**

## 3. 핵심 발견 — 지금 구조로는 「주춤」이 수학적으로 불가능하다

`stage_trigger_worker.py:813-816`:

```python
should_fire = (mark >= trigger) if side == "SHORT" else (mark <= trigger)
if not should_fire:
    continue          # ← 로그도 Redis 기록도 없다
```

SHORT 이 신고점 `H ≥ trigger` 를 찍고 δ 만큼 되돌아오면
`mark = H(1−δ)` 가 **trigger 아래로 내려가** 이 줄에서 죽는다. LONG 도 대칭.

간격이 1.9~2.1% 이므로 H 가 trigger 를 조금만 넘으면 **어떤 되돌림도 통과 불가**다.

> **즉 「주춤을 기다려라」를 지금 자리에 얹으면, 가격 게이트가 그 주춤을 스스로 막는다.**

### 해법 — 조건을 더하지 말고, 판정 **주체**를 바꾼다

```
현행 :  mark 가 trigger 에 도달했는가          (순간값)
신규 :  EXT  가 trigger에 도달했는가  AND  거기서 되돌아왔는가
        (EXT = 직전 단계 체결 이후의 러닝 극값)
```

`trigger_price` 계산(3/5/7·재앵커 Fix 209·죽은단계 검산)은 **한 줄도 건드리지 않는다.**
비교 대상만 `mark` → `EXT` 로 바꾼다.

## 4. 판정식

### 상태 (DB, `strategy_stage_plans` 에 신설)

| 컬럼 | 타입 | 뜻 |
|---|---|---|
| `peak_price` | NUMERIC(20,8) NULL | 직전 단계 체결 이후의 불리방향 극값 (EXT) |
| `peak_seen_at` | TIMESTAMPTZ NULL | 마지막으로 극값이 **갱신된** 시각 |
| `peak_renewed` | BOOLEAN DEFAULT false | 이 단계 대기 중 극값이 **재갱신**되었는가 (3단계용) |

🚨 Redis 가 아니라 **DB** 다. 재기동 후에도 유지되어야 사장님의
"다시 최고점으로 가면 다시 대기해서" 가 성립한다.

### 매 사이클 (15초) — 극값 갱신

```
if peak is None:          peak ← mark
elif s*mark > s*peak:     peak ← mark ; peak_seen_at ← now
                          if 현재 대기 단계 >= 3:  peak_renewed ← true
```

### 2단계 = 「최고점으로 가다가 주춤할때」

| # | 조건 | 식 | 원문 대응 |
|---|---|---|---|
| ① | 신고점 도달 | `s*EXT >= s*trigger_price` | "최고점으로 **가다가**" |
| ② | 되돌림 | `pull >= STALL_MIN` | "**주춤**할때" |
| ③ | 갱신 정지 | `now - peak_seen_at >= STALL_BARS × 15분` | "주춤" (지속) |

```
pull = s * (EXT - mark) / EXT * 100
```

### 3단계 = 「다시 최고점으로 가면 다시 대기해서 꺾이면」

2단계 조건의 반복이 **아니다**. 재갱신을 반드시 요구한다.

| # | 조건 | 식 | 원문 대응 |
|---|---|---|---|
| ① | 신고점 재도달 | `s*EXT >= s*trigger_price(3단계)` | "다시 최고점으로 가면" |
| ② | **재갱신 확인** | `peak_renewed == true` | "**다시**" |
| ③ | 갱신 정지 | `now - peak_seen_at >= TURN_BARS × 15분` | "다시 **대기해서**" |
| ④ | 더 깊은 되돌림 | `pull >= TURN_MIN` (> STALL_MIN) | "**꺾이면**" |

「주춤」(2단계)과 「꺾임」(3단계)은 **강도가 다르다** — 같은 임계를 쓰면 원문 오독이다.

## 5. 임계값 — 실거래 18건 시뮬레이션으로 정했다

### 방법

최근 4일 `split_entry` 18건에 대해 진입 시각부터 15m 봉을 다시 받아,
자본 100/200/500 · 레버 2x · TP +15% · SL 평단 ROI −10% 로 상태기계를 돌렸다.

### 🚨 첫 시도는 실패했고, 그 실패가 답을 줬다

사장님 규칙을 그대로 코딩하니 현행보다 **나빴다** (−2.56% vs −0.67%).
원인은 내가 원문의 **"최고점으로 *가다가*"** 에서 「가다가」를 빠뜨린 것이었다.
아무 극값 갱신이나 다 세고 있었다.

「가다가」= **극값이 최소 N% 나아갔을 것** 을 넣자 결과가 뒤집혔다.

### 파라미터 지형 (USDT 손익)

```
현행(1단계만 도는 지금)                        -12.22

          최소전진 ->   1.0%    1.5%    2.0%    2.5%
주춤 4봉               +24.3   +83.8   +99.3   +99.3
주춤 5봉               +15.8   +78.4   +97.4   +97.4
주춤 6봉               -29.4   +31.3   +25.4   +25.4
주춤 7봉               -30.3   +29.7   +25.5   +25.5
```

- **「최소 전진」이 지배 변수**다. 1.0% 면 무너지고 2.0% 부터 평평(포화)하다.
- 주춤 봉수는 4~5봉이 좋고 6봉부터 늦는다.
- 2.0% 와 2.5% 가 동일 = 그 위로 데이터가 없음 = **더 엄격해도 손해 없음**

### 과적합 검사 — 통과

```
최근 절반 9건 :  현행 +15.09  ->  규칙 +23.30
이전 절반 9건 :  현행 -27.31  ->  규칙 +55.13
```

**양쪽 다 개선.** 한쪽에만 맞은 우연이 아니다.

### 확정 임계

| 상수 | 값 | 근거 |
|---|---|---|
| **최소 전진** | `trigger_price` 그대로 (= gap 1.94~2.11%) | 시뮬 최적 2.0% 와 **기존 gap 이 일치**. 새 숫자를 만들지 않는다 |
| `STALL_BARS` | **5봉** (75분) | 4봉과 손익 차 2% 뿐. 봉수가 클수록 whipsaw 에 강함 |
| `STALL_MIN` | **0.40 × gap** (≈0.78~0.83%) | 절대값이 아니라 gap 비율 — 사장님이 3/5/7 을 바꿔도 자동 정합 |
| `TURN_BARS` | **5봉** | 2단계와 동일. 강도 차이는 되돌림 폭으로 준다 |
| `TURN_MIN` | **0.55 × gap** (≈1.07~1.16%) | 「꺾임」 > 「주춤」. 상한 검산 결과 0.70 은 통과 창이 0.07%p 로 사실상 불가라 내렸다 |
| `RENEW_EPS` | **0.15 × gap** (≈0.30%) | 재앵커가 같은 값으로 보는 기준 0.01% 의 30배 = 노이즈 위 |

⚠️ **`STALL_MIN` / `TURN_MIN` / `RENEW_EPS` 는 표본이 없다.** gap 비율로만 잡은 초기값이다.
`STALL_BARS` 와 최소 전진만 실측 근거가 있다.

⚠️ **3단계는 이 표본에서 거의 발동하지 않았다** (평균 도달 단계 1.33).
꺾임 임계 1.0% 와 2.0% 가 완전히 같은 값이 나온 이유다. **3단계 조건은 미검증이다.**

## 6. 배선 — 반드시 지킬 3가지

### ① 넣을 자리 = `stage_trigger_worker.py:865` (Fix 218 블록을 **교체**)

`stage_trigger` 는 `scheduler_runner.py:540` 에서 **enable 플래그 없이** 15초마다 등록된다.
꺼진 워커에 배선하는 Fix 256 함정은 이 경로에 해당 없음.

🚨 **`:953-1104` 의 Fix 55/114 블록에는 넣지 말 것.**
조건이 `not _is_split AND not _is_price_mode AND not _is_obv_mode` 인데
split 템플릿은 `trigger_mode` 기본값이 `PRICE_DOWN_PCT` 라 `_is_price_mode=True` 가 된다.
→ **현재 운영 조합 전부에서 한 번도 실행되지 않는 죽은 블록이다.** 넣으면 0사이클.

### ② `:814` should_fire 를 split 2·3단계만 분기

```python
if _is_split and next_stage_no >= 2:
    should_fire = (s * EXT >= s * trigger)        # mark 가 아니라 EXT
else:
    should_fire = (mark >= trigger) if SHORT else (mark <= trigger)   # 기존 그대로
```

이걸 안 하면 3장에서 증명한 대로 **되돌림이 통과할 수 없다.**

### ③ 🚨 발주는 반드시 MARKET

`execution_service.py:1108` — `trigger_price` 가 있으면 **LIMIT @ trigger_price** 로 나간다.
주춤 시점의 mark 는 trigger 반대편이므로 **그 LIMIT 은 체결되지 않는다.**

그런데:
- `current_stage` 는 발주만으로 올라가고 (`execution_service.py:250-252`)
- `reconcile_worker.py:509-528` 이 2분 뒤 「포지션 != 0」만 보고 `is_triggered=True` 로 거짓 회복

→ **자본은 안 들어갔는데 단계는 소진되고, 좀비 LIMIT 이 호가창에 남는다.**

**대책: 이 경로는 `trigger_price=None` 으로 넘겨 MARKET 진입시킨다.**
(`execution_service.py:1035-1085` 의 Fix 130 경로 = planned_capital 기준 수량 재계산 + preflight)

## 10. 알려진 한계 (정직한 선언)

1. **표본 18건 / 4일.** 방향은 견고해 보이나 숫자 자체는 더 쌓이면 다시 재야 한다.
2. **3단계 조건 미검증.** 표본에서 거의 발동하지 않았다.
3. **신고점·주춤의 승/패 분포는 이 프로젝트에서 한 번도 측정된 적이 없다.**
   `STALL_MIN` 등은 gap 비율로 잡은 초기값이며, 실측 분포 사이에 둔 값이 아니다.
4. 시뮬레이션은 15m 종가 기준이다. 실엔진은 15초 mark 를 보므로 **더 민감하게** 발동한다.
