## How to apply (반드시 이 순서)

### 코드를 고치기 **전에**:
1. **호출 체인을 끝까지 확인** — 내가 고치려는 함수가 **실제로 불리는 그 함수**인가?
   (같은 이름의 비슷한 함수가 둘 이상 있는지 반드시 grep)
2. **Agent / Workflow 로 검증** — 사장님이 정하신 5종:
   - **참조 필드 존재 확인** (모델에 그 필드가 실제로 있는가)
   - **함수/import 존재 + 시그니처** (인자 개수·이름, 반환 튜플 길이)
   - **SQL 문법 + 테이블·컬럼명** (`strategies`(X) vs `strategy_instances`(O))
   - **다른 파일과 호환성** (시그니처·반환값 변경이 깨는 곳)
   - **fail-open / fail-closed 방향이 옳은가** (주석이 선언한 방향과 코드가 같은가)
3. 검증 통과 → commit → 배포
4. 지적 → 수정 → **재검증**

### 큰 fix (필수)
3+ 파일 / DB 스키마 참조 / 신 외부 함수 호출 / **공용 함수 시그니처 변경**

### 작은 fix (skip 가능)
typo, 주석

## 예외 (즉시 처리 OK — 단 사고 위험을 명시 안내)
- 실 자금 위험 fix (사장님 자본 보호)
- 사장님 직접 지시 fix
→ 이 경우에도 **최소한 호출 체인 확인 + 정적 검사**는 하고 커밋한다.

## 🔁 재발 방지 체크 (커밋 전 스스로 묻기)
- [ ] 내가 고친 함수가 **실제로 불리는** 그 함수가 맞나? (동명이의 함수 확인)
- [ ] 반환값/시그니처를 바꿨다면 **모든 호출부**를 갱신했나?
- [ ] 이 변경이 **다른 전략**의 설계를 부수지 않나? (전역 설정이면 특히)
- [ ] 실패하면 어느 쪽으로 떨어지나? 그게 **사장님 자금에** 안전한가?
- [ ] 배포 후에만 알 수 있는 것을 **배포 전에** 확인할 방법이 있었나?
