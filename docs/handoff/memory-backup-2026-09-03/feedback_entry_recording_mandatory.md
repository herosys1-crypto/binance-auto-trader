# 🚨 진입 근거 기록은 **필수**다 — 두 번 놓쳤다

사장님 verbatim (2026-08-29):
> "분명이 이것을 학습하고 메모리에 저장하라고 했는데 정말 믿을수 없네 왜 이러는거지
>  오케스트라 지휘자는 뭘한거야 확실하게 꼭 이것을 학습하고 포지션 진입시 기록 메모리해서
>  차후에 분석하고 활용할수 있게 꼭만들어서 활용해"

**Why:** 사장님은 「실패한 진입을 분석해서 조건을 올리고, 성공한 진입을 참조해서 만들라」고
요구하신다. 그런데 진입 시점 근거가 안 남으면 **그 요구 자체가 영원히 불가능**하다.
감으로 임계값을 올리는 것은 사장님이 원하는 게 아니다.

## 내가 실제로 무엇을 잘못했나 (변명 없이)

1. **찾아놓고 안 고쳤다.** `entry_context` 가 전건 비어 있다는 걸 감사에서 확인해
   메모리에 적어두고도(`project_2026-08-27_pyramid_bbsplit_tp20` 미해결 항목),
   **기록 코드 자체는 손대지 않았다.** 기록하는 것과 아는 것은 다르다.
2. **죽은 상수를 조일 뻔했다.** `RSI_OVERSOLD_MAX` / `RSI_MIN_TURNUP` /
   `CCI_OVERSOLD_MAX` / `CCI_MIN_TURNUP` 은 **정의만 있고 어디서도 안 쓰인다.**
   grep 으로 확인하지 않았다면 "조건을 올렸다"고 보고하고 아무 일도 안 일어났을 것이다.
   (`OBV_MIN_SLOPE_PCT` 만 실제 사용 — auto_long_at_bottom_worker:266)

## 실측 — 기록이 반쪽이고 값도 깨져 있다 (2026-08-29)

`StrategySuggestion.strategy_config["entry_snapshot"]` (LONG, 종료건 승 30 / 패 107):

| 필드 | 승리 | 패배 | 문제 |
|---|---|---|---|
| `obv_slope_pct` | 15건 중앙 2.59 | 53건 중앙 2.46 **최대 2,249,160** | 계산 파손 + 절반 결손 |
| `rsi` | 15건 중앙 52.72 | 54건 중앙 48.76 | 결손 + 변별력 약함 |
| `cci` | **4건** | 18건 | 대부분 결손 |
| `change_24h` | 20건 | 90건 | 결손 |
| `confidence` | 0.88 전부 | 0.88 전부 | **변별력 0** (하드코딩 의심) |

→ **지금 기록으로는 성공/실패를 구분할 수 없다.** 중앙값이 승패 간 거의 같다.
→ OBV 최대 2,249,160 은 % 단위일 수 없다. 게이트(>= 1.0)가 **무력화**됐을 가능성.

## How to apply

- **진입 판정에 쓰인 원시값은 전부 남긴다** — 통과/탈락 bool 이 아니라 비교한 숫자 그대로.
- **경로가 여러 개면 경로마다 같은 스키마로** 남긴다 (알림 경유 / 직접 판정 등).
  경로별로 채우는 필드가 다르면 사후 분석이 불가능해진다.
- **기록 누락을 스스로 감지**하게 한다 — 필드 누락률을 로그로 남긴다 (헌법 80/93 정신).
- **임계값을 바꾸기 전에 반드시** ① 그 상수가 실제로 쓰이는지 grep ② 성공/실패 분포 비교.
  둘 중 하나라도 못 하면 「데이터가 없어서 못 한다」고 말할 것. 감으로 올리지 말 것.
- 조건 변경 제안 시 **승리 진입의 분포**를 근거로 제시한다 (사장님 요구: "성공한 진입을 참조").
